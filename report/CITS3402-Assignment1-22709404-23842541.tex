\section{Introduction}
%==============================================================================

This document outlines how the puzzling results of the Birthday Paradox can be
exploited in order to brute force hash collisions. The goal is to alter the 
`nonce' values in two PDF files, each with differing contents, in such a way 
that the resultant hash is identical. This collision is produced through the combination of nonce variation and the 
Birthday Attack principle, which proves that collision probability increases 
rapidly with less trials than is intuitively expected. 

%==============================================================================
\section{Birthday-Attack Algorithm}
\label{sec:bday}
%==============================================================================

The implemented search strategy uses a Hash-Table data structure to store and 
search through calculated hashes. Rather than comparing every possible 
nonce produced from one PDF file to the other, each calculated (hash+file) 
combination is stored in the hash table. Then when a new hash is generated, it is
compared against those previously stored in the table. 

The $\texttt{toy\_hash()}$ algorithm produces 48-bit hashes, giving $2^{48}$ 
possible hash outputs. Using the Birthday Paradox, the expected number of trials for 
a 50\% collision probability follows $2^{\sqrt{48}}=2^{24}$, or ~16-17 million values, 
are required to achieve a 50\% collision probability.
The probability of no collision occurring can be calculated using the following: 
$P(\text{No Collision})\approx e^{-\frac{n^2}{2H}}$, where $n$ is the 
number of trials required to achieve $P$ probability where there 
are $H$ possible outputs. For a 99\% chance of producing a collision:

$$0.01=e^{-\frac{n^2}{2\times2^{48}}}\quad\rightarrow\quad n\approx51,000,000$$

The loop is limited to 50,000,000 iterations, giving a high probability of producing 
a collision while limiting the memory being used.

To store and find collisions, the hash table uses linear probing. Each $\texttt{HashEntry}$ 
contains a 64-bit tag and 64-bit nonce, 16 bytes total. The $\texttt{tag}$ attribute combines 
the PDF number with the corresponding 48-bit file hash, allowing the program to distinguish 
hashes between PDFs. This table is initialised using $\texttt{calloc}$, representing empty 
slots with 0. The lowest 27 bits of the hash are used to to find the first insertion index 
to try, where the linear probing strategy is then used if it is occupied.

%==============================================================================
\section{Parallelisation with OpenMP}
%==============================================================================

The serial implementation assings a different nonce to each PDF in 
every iteration, then calculating the hash for both files. These hashes 
are then checked against the hash table using $\texttt{insert\_or\_match()}$. 
If either hash matches one which was produced by the other PDF, a collision/match 
is found and the nonces are returned. If not, then both hashes are inserted and 
the program continues searching.

\begin{center}
    \begin{tabular}{l}
        $\mid$ 1. Set and insert nonces into PDF 1 and 2\\
        $\mid$ 2. Calculate hash of each PDF\\
        $\mid$ 3. Check hash table\\
        $\hookrightarrow$ 3a. If match: save nonces and stop\\
        $\hookrightarrow$ 3b. If not: insert hashes into table and continue
    \end{tabular}
\end{center}

The parallel implementation splits the nonce generation and hashing across multiple 
threads in a $\texttt{parallel}$ region, using a $\texttt{for}$ with $\texttt{schedule(static)}$. 
Static scheduling is the ideal choice for this as each iteration does a similar amount of work.

Each thread creates local copies of the two PDFs so that $\texttt{set\_nonce()}$ 
can alter nonces without interference between threads, preventing a data race and threads 
overwriting each others PDF contents during hash calculations. The hash 
table is shared between all threads, so the lookup and insertion operations are 
isolated inside a $\texttt{critical}$ region. Without this region, numerous threads could 
concurrently access the same location in the hash table, potentially leading to the table being 
inconsistent.

The computationally expensive operations of $\texttt{set\_nonce()}$ and $\texttt{toy\_hash()}$ 
are deliberately left outside the critical region. This minimises the wait time for threads to 
access the shared hash table and allows most computation to continue simultaneously.

The $\texttt{found}$ variable is also shared, and is therefore synchronised in the parallel 
code using an $\texttt{atomic read}$ before each iteration proceeds with their computation 
(skipping the expensive functions if $\texttt{found}$ is true). Inside the critical region it 
is checked again, as a thread may have found a collision between the initial check and the 
critical region. This makes sure the first detected collision is used, avoiding unnecessary 
computation.

%==============================================================================
\section{Memory Usage \& Trade-Offs}
%==============================================================================

The hash table size is set as $2^{27}\times16$ bytes, capping 
the memory at just over 2GB. This was chosen to ensure that the maximum 
50,000,000 trials (for each PDF) can be stored while leaving space 
to minimise hash table probing conflicts. While dynamic hash table 
sizing could be more memory efficient, runtime resizing would increase the 
execution time. Therefore the initial allocation was large to improve speed.

Using a single critical region instead of a partitioned hash table was another 
trade-off. The region ensures correct access to the shared hash table, but only 
a single thread can access it at a time. While increasing the thread count can 
allow greater nonce generation and concurrent hashing, the table access becomes 
a bottleneck, limiting the speed-up. A partitioned table could reduce this by 
allowing threads to access partitions simultaneously. This was more complex to 
implement, so the simpler solution was chosen.

We observed that raw search times weren't monotonic with thread count, (e.g, Giga took 42.7 s on 64 threads but 170.6 s on 96 threads). We initially suspected this was due to the way NUMA caused  latency to the hash table's memory region, but, it turns out that the 96-thread run checked an estimated 33.9M pairs rather than 5.9M, while hashing $1.44\times$ faster. THis suggested that the static scheduling of the colliding nonces is the main factor in the elapsed time, not the speed of hashing. \\

Therefore, rather than using elapsed time, speedup was measured as a function of throughput (pairs checked / search time). A serial baseline would have been an inconsiderate use of HPC resources, thus, assuming linear scaling below the lowest measured thread count, speedup was calculated relative to the lowest thread count for each pair. This showed a near-linear speedup up to 48 threads for every pair, with efficiency ranging from 97-100\%.
